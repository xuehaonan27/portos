# portos-shell

跑一条命令，别把模型淹死在输出里。

一个动词。有意思的部分全在命令**周围**。

## `cmd` 是一整条交给 `sh -c` 的字符串

不是 `{bin, args[]}`，**故意的**：管道本身就是上下文纪律。

```
cargo test 2>&1 | tail -40
```

让 shell 先把输出压小，比事后分页读一个 artifact 便宜得多。代价是这个动词等于任意执行——与 `kernel::spawn` 的裁定一致，不再单独设限。

## 输出是数据面的问题

`stdout` / `stderr` 各自过 `portos_bulk_api::Sink`：≤16KB 内联，超了进 CAS 只回 `{handle, size, preview}`。

实测（本仓库）：`cargo test --workspace 2>&1` 输出约 **10KB，低于阈值所以内联**——这条纪律真正生效的是更大的东西（一次全仓 grep 是 765KB，上下文里只留 2048 字符）。

## timeout 收的是进程组，不是进程

`sh -c` 极少是真正干活的那个；它有子进程，子进程还有子进程。内核在插件身上学过这一课，这里是同一课：

命令以自己为组长启动（`process_group(0)`），超时后逐级升级 **组 SIGTERM → 组 SIGKILL**。

**而且升级本身不够。** 升级在组长一死就停下，可组长死了不代表组空了。所以调用返回前还有一次**无条件的组 SIGKILL**，超时与否都一样——内核清退插件时的最后一步正是这个。

这同时解决了第二个问题：一个后台孙进程会一直**攥着 stdout 管道**，只杀组长的话这个调用会挂在读管道上永远不返回。**挂死的是整个驱动，不只是漏一个进程。**

**由此而来的语义**：`shell::run` **不留下任何东西**。`some-daemon &` 活不过这次调用。要长期运行的东西是插件，不是后台作业。

两条各有一个测试：`a_timeout_collects_the_whole_process_group` 和 `a_background_child_does_not_survive_a_command_that_exits_normally`。

## 已知形状，写明

- **调用阻塞到命令结束。** turn 在命令跑到一半被取消，要等命令返回才察觉——取消只在每次工具调用**之前**检查。异步化的路是现成的（`model::send` 已经走过：接受即返回、自己的线程、事件面上欠恰好一个终结事件），值得走的时机是真的有人在等一个五分钟的构建，或者 console 要看实时输出。
- **SDK 的 serve 循环单线程**，所以一条长命令期间本驱动其它调用排队。
- **`cwd` 只是默认值，不是围栏。** `cd /` 一句就出去了。这里不制造安全感。

## 配置

- `PORTOS_SHELL_CWD` —— 默认工作目录，不设则用进程自己的。
- 默认 timeout 120s，可由 `timeout_ms` 逐次覆盖。
